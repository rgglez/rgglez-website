## Introduction

Le 20 octobre 2026, tard dans la soirée, je suis tombé sur
<a href="https://x.com/midudev/status/2112812718856044738" target="_blank">une
publication de @midudev sur X</a> qui a attiré mon attention (et m’a laissé avec
cette tête 😨). Une série de vulnérabilités critiques avait été découverte dans
PHP. Elle permettait d’obtenir facilement un shell sur les serveurs compromis.
Des correctifs étaient annoncés pour le lendemain, le 21 octobre. Ces
vulnérabilités ont reçu le nom de **PHP2Shell**.

<YouTubeEmbed id="CuvRrItIdKs" title="@midudev: ¡Han hackeado PHP!" />

Ces vulnérabilités sont particulièrement inquiétantes, car de nombreux sites web
utilisent PHP et leur exploitation est relativement simple pour une personne
ayant des connaissances de base. PHP est l’un des langages les plus utilisés
pour le développement web. De nombreuses applications populaires en dépendent,
notamment WordPress, Joomla et Drupal. Leur exposition pourrait donc avoir des
conséquences importantes sur la sécurité du Web.

Leur score est de 9,2 sur 10 dans l’échelle CVSS v4.0. Leurs identifiants sont
<a href="https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w" target="_blank">CVE-2026-109618</a>
et
<a href="https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp" target="_blank">CVE-2026-109619</a>.

Des chercheurs de Wiz, Calif et OpenAI auraient découvert ces erreurs à l’aide
de l’intelligence artificielle et commencé à les signaler le 11 août 2026. Des
<a href="https://watchtowr.com/intelligence/php-remote-code-execution-php2shell/" target="_blank">exploits
publics</a> semblent déjà disponibles. Des attaquants pourraient ainsi
compromettre des serveurs web sans connaissances avancées.

Les vulnérabilités touchent toutes les versions de PHP depuis la 5.4, publiée le
1er mars 2012. Selon la PHP Foundation, un audit du code réalisé en 2024 avait
déjà repéré ces problèmes, mais des processus internes et la crainte de rompre
la compatibilité avaient retardé leur correction.

## Comment les vulnérabilités sont exploitées

Le principal risque est la possibilité pour un attaquant d’exécuter du code
arbitraire directement sur le serveur web touché. Une connexion au serveur
exécutant la version vulnérable de PHP suffit. L’attaquant pourrait prendre le
contrôle du serveur, accéder à des données sensibles, modifier des fichiers,
installer des logiciels malveillants ou utiliser le serveur pour attaquer
d’autres systèmes. PHP s’exécute normalement sous le compte du serveur web,
comme `www-data` ou `nobody`. Si le serveur est mal configuré ou présente
d’autres vulnérabilités, l’attaquant pourrait élever ses privilèges et obtenir
un accès complet en tant que `root`. Même sans cela, l’exécution de code sous le
compte du serveur web reste un risque majeur. L’attaquant pourrait, par exemple,
installer un web shell pour parcourir les fichiers, les lire et les modifier,
puis lancer des commandes système depuis un navigateur. Il pourrait aussi
installer un logiciel malveillant pour voler des identifiants, des données de
cartes bancaires ou des renseignements personnels. Enfin, le serveur compromis
pourrait servir à mener des attaques DDoS, miner des cryptomonnaies, se déplacer
latéralement dans le réseau ou envoyer du spam.

<Aside title="Note de sécurité">

L’exploitation de ces vulnérabilités ne demande pas de compétences avancées en
programmation ou en piratage. Une personne ayant des connaissances de base
pourrait utiliser des outils automatisés disponibles en ligne. Les
administrateurs système et les développeurs web doivent donc agir immédiatement
pour protéger leurs serveurs et leurs applications.

Les applications n’ont pas besoin de présenter leurs propres failles pour être
vulnérables à PHP2Shell. Les défauts se trouvent dans l’interpréteur PHP
lui-même. Toute application exécutée avec une version vulnérable de PHP pourrait
donc être exposée, qu’il s’agisse de WordPress, de Joomla, de Drupal ou d’une
application développée en interne.

</Aside>

## Correctifs et atténuation

La mise à jour de PHP est le seul moyen efficace d’atténuer ces vulnérabilités.
De nombreuses versions touchées ne bénéficient plus du support officiel, mais
peuvent encore être utilisées. Les administrateurs et les développeurs doivent
passer à une version de PHP contenant les correctifs de sécurité. Si un serveur
web touché ne peut pas être mis à jour, mets-le hors ligne et actualise ses
applications avant de l’exposer à nouveau à Internet.

| **Branche PHP** | **Versions vulnérables** | **Première version sûre** |
| :-------------- | :----------------------- | :------------------------ |
| 8.5             | Avant la 8.5.12          | 8.5.12                    |
| 8.4             | Avant la 8.4.27          | 8.4.27                    |
| 8.3             | Avant la 8.3.36          | 8.3.36                    |
| 8.2             | Avant la 8.2.35          | 8.2.35                    |

### Anciennes versions et rétroportages de sécurité

PHP 8.1 et les versions antérieures ne reçoivent plus de mises à jour du projet
PHP. PHP 8.2 arrivera en fin de vie le 31 décembre 2026. Pour les branches plus
anciennes, l’équipe de sécurité de PHP a publié des rétroportages pour PHP 7.4,
8.0 et 8.1 afin d’aider les personnes qui compilent PHP depuis les sources ou
attendent une mise à jour de leur fournisseur.

Le mainteneur indépendant
<a href="https://github.com/sponsors/oerdnj" target="_blank">Ondřej Surý</a> a
<a href="https://codeberg.org/oerdnj/deb.sury.org/issues/145" target="_blank">publié</a>
les 21 et 22 octobre 2026 des paquets corrigés pour toutes les branches qu’il
maintient, de PHP 5.6 à PHP 8.5. La section plus bas explique comment en
vérifier un. Ubuntu, de son côté, a déjà publié des mises à jour de sécurité
pour PHP 7.4, 8.0 et 8.1 dans ses dépôts officiels
<a href="https://ubuntu.com/blog/php2shell-vulnerability-fixes-available" target="_blank">Ubuntu
Expanded Security Maintenance</a>.

### Atténuation temporaire

De nombreux sites évoquent des mesures temporaires, comme la désactivation de
certaines fonctions PHP ou la réduction de valeurs de configuration. Ces mesures
ne sont pas totalement efficaces et ne garantissent pas la sécurité du serveur.
Pour le protéger complètement, mets PHP à jour vers une version sûre, puis
redémarre le processus ou le serveur pour t’assurer que la nouvelle version est
utilisée.

## Mon serveur est-il encore vulnérable ?

La vérification se fait sur le serveur lui-même et n’ouvre aucune connexion.
Compare le binaire en cours d’exécution avec le paquet qui contient déjà le
correctif. `php -v` ne suffit pas. Ce n’est pas forcément l’interpréteur qui
sert le site, et une distribution peut appliquer le correctif sans changer le
numéro de version de PHP.

<Aside title="Ne déclenche pas la faille" type="danger">

  N’envoie pas de requête de test et n’utilise pas un scanner distant pour voir
  si le serveur est vulnérable. Ces scanners épuisent la mémoire exprès pour
  vérifier si le worker plante. C’est la faille, pas une vérification, et cela
  peut interrompre les requêtes que ce worker traitait déjà.

</Aside>

### Le paquet présent sur le disque

Sous Ubuntu ou Debian, inutile de sortir sur le réseau. Ces deux commandes
lisent ce qui est déjà installé.

```bash
apt list '?installed ?name(^php[0-9.]+$)'
zgrep -l -i -e 109618 -e 109619 /usr/share/doc/php*/changelog.Debian.gz
```

Si le CVE n’apparaît pas dans le journal des modifications du paquet utilisé
par le site, ce binaire n’est pas corrigé. Ne compare pas les chaînes à l’œil.
`8.3.6-0ubuntu0.24.04.9` est antérieure à `8.3.6-0ubuntu0.24.04.13`, même si 9
semble plus grand que 13. Laisse `dpkg` le faire.

```bash
dpkg --compare-versions '8.3.6-0ubuntu0.24.04.9' ge '8.3.6-0ubuntu0.24.04.13'
echo $?
```

Cet exemple se termine par `1`. Le premier argument n’est pas supérieur ou égal
au second. Quand tu compares ton paquet, un `0` signifie que tu as atteint la
version de droite.

<a href="https://ubuntu.com/blog/php2shell-vulnerability-fixes-available" target="_blank">Ubuntu
a publié ces correctifs</a>
le 21 octobre 2026. La première version qui contient le correctif est celle du
tableau. 22.04 et les versions suivantes relèvent du support standard. 20.04 et
18.04 passent par Expanded Security Maintenance. 16.04 et 14.04 exigent en plus
le complément Legacy.

| **Ubuntu** | **Paquet** | **Première version corrigée**  |
| :--------- | :--------- | :----------------------------- |
| 26.10      | php8.5     | 8.5.9-0ubuntu2.1               |
| 26.04      | php8.5     | 8.5.4-0ubuntu1.5               |
| 24.04      | php8.3     | 8.3.6-0ubuntu0.24.04.13        |
| 22.04      | php8.1     | 8.1.2-1ubuntu2.28              |
| 20.04      | php7.4     | 7.4.3-4ubuntu2.29+esm5         |
| 18.04      | php7.2     | 7.2.24-0ubuntu0.18.04.17+esm14 |
| 16.04      | php7.0     | 7.0.33-0ubuntu0.16.04.16+esm22 |
| 14.04      | php5       | 5.5.9+dfsg-1ubuntu4.29+esm18   |

Sous Debian, la vérification est le même journal des modifications. Ne
considère pas le paquet comme corrigé seulement parce que `php -v` affiche un
numéro. Sous RPM, cherche l’avis dans le paquet réellement installé. Le nom
change selon la branche.

```bash
rpm -q --changelog php-fpm | grep -e 109618 -e 109619
```

Si tu as compilé PHP depuis le code de php.net, le numéro de version compte.
Les premières versions sûres sont 8.5.12, 8.4.27, 8.3.36 et 8.2.35, celles du
tableau de la section précédente. Le projet ne publie pas de correctif pour
8.1 ni pour les versions antérieures. Un 8.1.2 d’Ubuntu 22.04 peut être
corrigé. N’importe quel 8.1 téléchargé depuis php.net ne l’est pas.

### Les paquets d’Ondřej Surý

Le tableau d’Ubuntu ne sert pas si PHP vient de `ppa:ondrej/php` ou de
<a href="https://packages.sury.org/php/" target="_blank">packages.sury.org</a>.
Ces paquets ont leur propre révision. Un 8.1.34 peut être antérieur au
correctif, et un 8.3.6 d’Ubuntu ne se compare pas à un 8.3.36 de Surý.

Regarde d’abord d’où vient le paquet. Remplace `php8.3` par la branche qui sert
le site.

```bash
apt-cache policy php8.3
```

Si l’origine est `packages.sury.org` ou `ppa.launchpad.net/ondrej/php`, ignore
le tableau d’Ubuntu. Le journal des modifications reste la preuve. Le `zgrep`
ci-dessus doit mentionner `109618` ou `109619`.

S’il n’y a pas de journal, compare avec la révision que ce dépôt a publiée les
21 et 22 octobre 2026. Je l’ai consultée le 24 octobre pour Debian 11, 12 et
13, ainsi que pour Ubuntu 22.04 et 24.04. Le suffixe `+debian12` ou
`+ubuntu24.04` change selon le système. La partie qui compte est celle de
gauche, epoch compris. PHP 7.4 et PHP 8.0 en ont un.

| **Paquet** | **Révision minimale** |
| :--------- | :-------------------- |
| php8.5     | 8.5.12-1              |
| php8.4     | 8.4.27-1              |
| php8.3     | 8.3.36-1              |
| php8.2     | 8.2.35-1              |
| php8.1     | 8.1.34-9              |
| php8.0     | 1:8.0.30-25           |
| php7.4     | 1:7.4.33-31           |
| php7.3     | 7.3.33-35             |

| php7.1     | 7.1.33-81             |
| php7.0     | 7.0.33-93             |

`php8.6` n’est pas dans le tableau. Ce jour-là, l’index publiait encore
`8.6.0~rc3`, compilé le 12 octobre. Ne le considère pas comme corrigé.

```bash
dpkg --compare-versions "$(dpkg-query -W -f '${Version}' php8.1)" ge '8.1.34-9'
echo $?
```

Un `0` signifie que le paquet installé atteint cette révision. Un `1` signifie
que non. Ne compare pas avec `8.1.34` seul. `8.1.34-8` est antérieur à
`8.1.34-9`, et c’est la seconde qui apporte le correctif. Si l’origine est le
PPA et que la version ne correspond pas, fie-toi au journal des modifications.

### Le processus encore en mémoire

Mettre le paquet à jour ne remplace pas le code déjà chargé. Le worker conserve
l’ancien binaire jusqu’au redémarrage. Regarde l’exécutable du processus, pas
le nouveau fichier sur le disque.

```bash
ps -eo pid,lstart,cmd | grep -E '[p]hp-fpm|[a]pache2|[h]ttpd'
sudo readlink /proc/PID/exe
```

Remplace `PID` par celui de la première colonne. N’utilise pas `readlink -f`.
Cette option résout le chemin actuel et masque l’information utile. Si la
sortie se termine par `(deleted)`, le processus exécute encore le binaire
d’avant la mise à jour.

Avec mod_php, le processus est Apache. Le fait qu’`apache2` ne dise pas
`(deleted)` ne prouve rien, car le code vulnérable se trouve dans `libphp*.so`.
Vérifie la carte mémoire du processus.

```bash
sudo grep 'libphp' /proc/PID/maps
```

Si cette ligne se termine aussi par `(deleted)`, Apache utilise encore
l’ancien module. Redémarre PHP-FPM, Apache ou le service concerné, puis
exécute de nouveau les deux commandes. L’heure de `lstart` doit être
postérieure à la mise à jour.

Fais-le pour chaque binaire. Un serveur peut avoir `php8.2-fpm` et `php8.3-fpm`
en même temps, et le site peut utiliser celui que tu n’as pas mis à jour. Le
`php` du `PATH` n’est pas forcément l’un des deux.

### PHP dans un conteneur

Le `php` de l’hôte ne dit rien du conteneur. Entre dans le conteneur, ou
inspecte l’image, et répète les deux vérifications. Si l’image a été construite
avant le correctif, le site reste vulnérable même si l’hôte est déjà à jour.

Un résultat propre signifie que ce processus exécute un binaire corrigé. Il ne
signifie pas que personne n’est entré avant le redémarrage. C’est l’objet de la
section suivante.

## Mon serveur a-t-il été compromis ? Reste-t-il des traces ?

Le script suivant ne peut pas déterminer si quelqu’un est entré dans un serveur.
Il fonctionne en lecture seule et recherche les erreurs que ces failles peuvent
laisser au démarrage d’une requête, ainsi que les plantages de workers, les
sessions et les processus enfants. Il lit les journaux d’Apache, de nginx et de
PHP-FPM, y compris les fichiers `.gz` archivés, ainsi que le journal de ces
services.

Une erreur fatale se terminant par `in Unknown on line 0` avec épuisement de la
mémoire est un indice de CVE-2026-109618. Une version de PHP déjà corrigée écrit
la même ligne lorsque la requête atteint `memory_limit`. Elle ne prouve donc pas
l’exploitation de la faille. CVE-2026-109619 peut survenir sans épuisement de la
mémoire. Elle peut se manifester par un délai dépassé ou par le plantage d’un
worker, avant même le démarrage d’un script.

Le journal des accès ne contient pas le corps des requêtes. Si PHP s’exécute
dans un conteneur, lance le script à l’intérieur. Un résultat sans alerte, ou
des journaux déjà supprimés par rotation, ne permettent pas de trancher.

Enregistre le script et exécute-le en tant que root. Il nécessite Bash 4 ou une
version ultérieure, ainsi que `gzip` pour lire les journaux archivés compressés.

**Lis le script et la note de sécurité qui le suit avant de l’exécuter.**

```bash
#!/bin/bash
# Triage en lecture seule pour PHP2Shell.
# CVE-2026-109618 / CVE-2026-109619.
#
# Ne prouve pas une compromission. Aucun résultat ne permet de l’exclure.
# PHP corrigé écrit aussi la même erreur fatale de mémoire.
# Le corps des requêtes ne figure pas dans le journal des accès.
#
# Utilisation : sudo bash php2shell-triage.sh

set -u

if ((BASH_VERSINFO[0] < 4)); then
  echo "Bash 4 ou une version ultérieure est nécessaire." >&2
  exit 1
fi

if [[ ${EUID:-$(id -u)} -ne 0 ]]; then
  echo "Exécute-le en tant que root pour lire les journaux : sudo bash $0" >&2
  exit 1
fi

RED=$'\033[31m'
YEL=$'\033[33m'
GRN=$'\033[32m'
NC=$'\033[0m'

SINCE=2026-10-20

# Erreur fatale avant que PHP ne démarre un script.
PRESCRIPT_RE='in Unknown on line 0'
# La seconde forme apparaît avec memory_limit=-1.
OOM_RE='Allowed memory size of [0-9]+ bytes exhausted|Out of memory \(allocated'
TIMEOUT_RE='Maximum execution time of [0-9]+ seconds exceeded'
# Apache écrit "exit signal Segmentation fault (11)", pas "exit signal 11".
CRASH_RE='exited on signal (4|6|7|8|11)|SIGSEGV|SIGBUS|SIGABRT|segfault at|Segmentation fault|zend_mm_heap corrupted'
UPSTREAM_RE='upstream prematurely closed connection'
# User-Agents publiés par ELLIO le 21 octobre 2026.
UA_RE='php2shell-scan/109618|php2shell-109618|php2shell-verify/'

WEB_COMM_RE='^(php-fpm[0-9.]*|php-cgi[0-9.]*|apache2|httpd|nginx|lsphp[0-9]*|frankenphp)$'
TOOL_RE='^(sh|bash|dash|zsh|curl|wget|nc|ncat|netcat|python[0-9.]*|perl|ruby|socat|base64)$'

declare -a ERR_LOGS=()
declare -a ACC_LOGS=()
declare -A SEEN_LOG=()
declare -A WEB_USER=()
GZ_WARNED=0

section() { printf '\n[+] %s\n' "$1"; }
note() { printf '  %s\n' "$1"; }
ok() { printf '%b  %s%b\n' "$GRN" "$1" "$NC"; }
lead() { printf '%b  %s%b\n' "$YEL" "$1" "$NC"; }
bad() { printf '%b  %s%b\n' "$RED" "$1" "$NC"; }

remember() {
  local kind=$1 f=$2
  [[ -f $f && -r $f ]] || return 0
  [[ -n ${SEEN_LOG[$f]:-} ]] && return 0
  SEEN_LOG[$f]=1
  if [[ $kind == err ]]; then
    ERR_LOGS+=("$f")
  else
    ACC_LOGS+=("$f")
  fi
}

remember_glob() {
  local kind=$1 pat=$2 f
  shopt -s nullglob
  for f in $pat; do
    remember "$kind" "$f"
  done
  shopt -u nullglob
}

collect_logs() {
  remember_glob err '/var/log/apache2/error.log*'
  remember_glob err '/var/log/httpd/error_log*'
  remember_glob err '/var/log/nginx/error.log*'
  remember_glob err '/var/log/php*-fpm.log*'
  remember_glob err '/var/log/php*-fpm/*.log*'
  remember_glob err '/var/log/php-fpm/*.log*'
  remember_glob err '/var/log/syslog*'
  remember_glob err '/var/log/messages*'
  remember_glob err '/var/log/kern.log*'
  remember_glob acc '/var/log/apache2/access.log*'
  remember_glob acc '/var/log/apache2/other_vhosts_access.log*'
  remember_glob acc '/var/log/httpd/access_log*'
  remember_glob acc '/var/log/nginx/access.log*'

  local raw path ini
  while IFS= read -r raw; do
    raw=${raw%%#*}
    set -- $raw
    [[ $# -ge 2 ]] || continue
    path=$2
    path=${path%;}
    path=${path//\"/}
    path=${path//\$\{APACHE_LOG_DIR\}/\/var\/log\/apache2}
    [[ $path == /* ]] || continue
    [[ $path == *\$* ]] && continue
    case $path in
      off|stderr|syslog) continue ;;
    esac
    case $1 in
      ErrorLog|error_log) remember_glob err "${path}*" ;;
      CustomLog|access_log) remember_glob acc "${path}*" ;;
    esac
  done < <(grep -rhsE '^[[:space:]]*(ErrorLog|error_log|CustomLog|access_log)[[:space:]]+' \
    /etc/apache2 /etc/httpd /etc/nginx 2>/dev/null || true)

  while IFS= read -r ini; do
    ini=${ini%%#*}
    ini=${ini#*=}
    ini=${ini//[[:space:]\"\;]/}
    [[ $ini == /* ]] || continue
    remember_glob err "${ini}*"
  done < <(grep -rhsE '^[[:space:]]*error_log[[:space:]]*=' \
    /etc/php /etc/php.ini /etc/php.d /etc/php-fpm.conf /etc/php-fpm.d 2>/dev/null || true)
}

is_syslog() {
  case $1 in
    */syslog*|*/messages*|*/kern.log*) return 0 ;;
    *) return 1 ;;
  esac
}

match_file() {
  local re=$1 file=$2
  if [[ $file == *.gz || $file == *.gzip ]]; then
    if ! command -v gzip >/dev/null 2>&1; then
      if ((GZ_WARNED == 0)); then
        printf '  %s\n' "gzip n’est pas installé. Les journaux .gz ne seront pas lus." >&2
        GZ_WARNED=1
      fi
      return 0
    fi
    gzip -dc -- "$file" 2>/dev/null | grep -E -- "$re" || true
  else
    grep -E -- "$re" "$file" 2>/dev/null || true
  fi
}

show_tail() {
  printf '%s\n' "$1" | tail -5 | sed 's/^/    /'
}

count_lines() {
  printf '%s\n' "$1" | grep -c .
}

load_web_users() {
  local u
  for u in www-data apache nginx http nobody www; do
    WEB_USER[$u]=1
  done
  while IFS= read -r u; do
    [[ $u =~ ^[A-Za-z0-9._-]+$ ]] || continue
    WEB_USER[$u]=1
  done < <(grep -rhsE '^[[:space:]]*(User|user)[[:space:]]+' \
    /etc/apache2 /etc/httpd /etc/nginx \
    /etc/php/*/fpm/pool.d /etc/php-fpm.d 2>/dev/null \
    | awk '{gsub(/[;=]/, " ", $0); print $2}' || true)
}

journal_units() {
  command -v systemctl >/dev/null 2>&1 || return 0
  systemctl list-units --type=service --all --no-legend --plain 2>/dev/null \
    | awk '{print $1}' \
    | grep -E '^(php.*fpm|apache2|httpd|nginx)\.service$' || true
}

echo "=== Triage PHP2Shell (lecture seule) — $(date) ==="
echo "Ne prouve pas une compromission. Un résultat sans alerte ne l’exclut pas."

collect_logs
load_web_users

J_ARGS=()
if command -v journalctl >/dev/null 2>&1; then
  while IFS= read -r unit; do
    [[ -n $unit ]] && J_ARGS+=(-u "$unit")
  done < <(journal_units)
fi

section "Journaux à lire"
if ((${#ERR_LOGS[@]})); then
  printf '  error: %s\n' "${ERR_LOGS[@]}"
else
  note "Aucun journal d’erreurs lisible. Les recherches ne verront rien."
fi
if ((${#ACC_LOGS[@]})); then
```

<Aside title="Note de sécurité sur le script" type="warning">

Il s’agit d’un triage, pas d’une enquête. Un résultat vert n’exclut pas une
compromission. Les sessions PHP sont supprimées après environ 24 minutes, le
journal des accès ne conserve pas le corps des requêtes et une personne ayant
obtenu l’accès root peut avoir effacé les journaux.

Si tu observes une erreur fatale avant le démarrage d’un script, le plantage
d’un worker ou un processus enfant inconnu, mets le serveur hors service et
conserve les journaux. Mets PHP à jour et réinstalle à partir d’une copie saine.
Supprimer uniquement le fichier suspect ne suffit pas.

Le script ne modifie pas le système. Lis-le avant de l’exécuter. Il a été créé
avec l’aide de Grok 4.7. Tu peux laisser tes remarques ou propositions
d’amélioration dans Giscus ci-dessous.

**Ce script est fourni à titre indicatif, en l’état et sans garantie. Aucune
responsabilité n’est assumée quant à son utilisation ou à ses résultats. Si tu
soupçonnes une compromission, il est vivement recommandé de mener une enquête de
sécurité complète et de consulter des spécialistes.**
